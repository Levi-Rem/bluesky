## 1. 总体结论

本分支实现了第二版的大量骨架，**纯函数/领域层质量普遍较高**（状态机边集与设计逐边一致、幂等与 Outbox 事务模型正确、错误码与消息类型契约全量一致、解析器约八成符合第 7 节语法、并发测试多为真实断言），但整体呈现**"纯函数层完成、接线层缺失"**的特征：

1. **多个核心链路在生产路径上是断的**：指令从 DISPATCHING 到终态的执行链路、v2 文本指令解析入口、删除 Saga 的 HTTP 入口与 Adapter 确认回路、动态帧/时钟推进、引擎健康监控（EngineHealthMonitor / AdapterStateSubscriber / SnapshotChunkAssembler 三件套零生产调用方）——这些类实现精良、单测齐全，但没有任何生产调用。
2. **存在生产阻断级缺陷**：V10 迁移回填 CHAR(36) 溢出（带存量数据升级必失败）、StartupReset 无条件清库（违反设计 3.3.7）、删除确认 token 可伪造可重放、DisplayProfileMapper 使用 H2 专用 MERGE 语法（MySQL 必报错）。
3. **v1 遗留路径仍活跃并与 v2 语义互相破坏**：v1 指令链路持续写 PENDING/APPEND、v1 物理删除入口在线、EngineStateMonitor 断连时直改 RUNNING→PAUSED 绕过状态机、前端 100% 仍跑在 /api/v1。
4. **分支实际范围已超出 Wave 1**（含 Wave 2 的指令内核/解析器/V11/V13、Wave 5 的假目标域、Wave 7 的归档件），但 Wave 1 自身的执行门 `M1AcceptanceTest` 不存在，且 Wave 1 要求的 P06/P07/P08 前端文件全部缺失。
5. 前端 `npm run typecheck` 失败，质量门未跑全。

按设计 1.1.6（"源码与本文不一致时默认判定为实现偏差"）与第 17 节完成定义衡量，当前状态距 Wave 1/M1 的完成口径有实质差距。

## 3. P0 问题（必须立即处理）

### P0-1 V10 迁移回填主键 CHAR(36) 溢出，带遗留数据的升级必然失败
- 位置：`training-platform/src/main/resources/db/migration/V10__v2_aircraft_plan_assignment.sql:92-98`
- `CONCAT(id,'-p1')` / `CONCAT(id,'-a1')`：v1 航空器 id 为 36 字符 UUID，拼接后 39 字符，目标列 `flight_plan.id`、`aircraft_assignment.id` 均为 CHAR(36)。MySQL 严格模式报 1406，迁移在任何存在 v1 航空器的库上中断且 DDL 不可回滚。
- 未被测试拦截的原因：`V10MigrationTest` 在迁移后才插入测试数据，回填 SELECT 始终作用于空表。
- 违反：设计 13.3（存量保留并迁移）、13.1（不修改已执行迁移，失败后无法安全重试）；TDD 第 3 节"MySQL 特性不得只用 H2 证明"。
- 修复：回填主键改用 `UUID()` 或独立派生；补"先注入 V9 前置遗留行再跑 Flyway"的迁移测试。

### P0-2 StartupReset 无条件注册，生产环境每次重启清空全部业务数据
- 位置：`training-platform/src/main/java/org/bluesky/training/configuration/StartupReset.java:14-33`
- 裸 `@Component implements ApplicationRunner`，无 `@Profile`/`@ConditionalOnProperty`，主 `application.yml` 无门控；每次启动执行 deleteInstructions → deleteAircraft → resetDefaultGroup + RESET。`StartupResetTest` 反而把破坏性行为固化为预期。
- 违反：设计 3.3.7（生产不执行启动清空）、13.5/17.5（重启后可恢复）；TDD P19 重构项 10。
- 修复：改条件装配（显式 demo/test 配置），P20 阶段彻底删除。

### P0-3 v2 删除/预览 HTTP 入口整体缺失，删除功能不可用
- 位置：`aircraft/AircraftControllerV2.java:92-94`（注释声称 DELETE 由 P15 的 AircraftDeleteControllerV2 暴露，该类不存在）；`cancelPlannedAircraft` 为无调用方死代码。
- `POST /aircraft/{id}/deletion-preview`、`DELETE /aircraft/{id}`、retry-delete、cancel-delete、取消未出现计划入口全部不存在；`DeletionPreviewService`/`AircraftDeletionSaga` 只被测试调用。
- 违反：设计 9.2 接口表、7.9 全流程、5.2.6；TDD P15。
- 修复：补齐 AircraftDeleteControllerV2（preview → token 原子消费 → DELETE → retry/cancel）。

### P0-4 AIRCRAFT_DELETE 响应无领域处理，删除确认回路断裂
- 位置：`adapter/AdapterActionResultService.java:58-100`（仅处理 AIRCRAFT_APPLY 与生命周期；`expectedResponseType:184` 定义了 AIRCRAFT_DELETE→AIRCRAFT_DELETED 却无任何分支）
- Adapter 确认删除后只 confirm Outbox 行，航空器永远停留 DELETE_REQUESTED；拒绝不进 DELETE_FAILED；无 5 秒超时→DELETE_FAILED；`DeletionReconciliationService`（EXISTS 对账、重启恢复）不存在。数据库与 BlueSky 长期分叉。
- 违反：设计 7.9（确认事务/超时/重启对账）、13.2.3。
- 修复：增加 AIRCRAFT_DELETE 分支（accepted→confirmDeleted、rejected→markDeleteFailed）+ 超时检测 + 启动时 resumeIncompleteSagas。

### P0-5 删除一次性确认 token 可伪造、可重放，"摘要落库、原子消费"未实现
- 位置：`instruction/DeletionTokenCodec.java:22-30`（encode 仅为 Base64(JSON)，无 HMAC 签名）；`DeletionPreviewService.java:55-88`
- 任何客户端可自造 revision/terminalId/未来过期时间的 token 绕过全部校验；`hashForStorage` 存在但无表落库、无消费记录，同一 token 30 秒内可无限重放；`createPreview` 把 tokenDigest 回给客户端。
- 违反：设计 7.9（"绑定航空器 ID + revision + 受信终端 + requestId 的一次性 30 秒确认 token"、token 摘要落库）；TDD P15 20.2.1-2。
- 修复：token 加 HMAC（密钥来自受限配置）；建 deletion_confirmation_token 表存 digest+consumed_at，消费用条件更新；响应不回 digest。

### P0-6 指令调度执行链路整体缺失，DISPATCHING 是死状态

- 修复：实现 dispatch 确认链路：BEGIN_DISPATCH 事务内 claim slot + 建 PENDING_APPLY 引导目标 + 写 Adapter Outbox（幂等键=instructionId）；确认/拒绝/超时分别驱动状态机并释放 slot。
