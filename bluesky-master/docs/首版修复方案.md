# 首版飞行仿真闭环代码审阅问题修复方案（核对版）

> 文档状态：已核对（2026-08-13）
> 依据报告：《首版代码审阅报告》（针对暂存区相对 HEAD 428ea3c 的文档与代码一致性审阅）
> 适用基线：《首版飞行仿真闭环详细设计》《程序管制训练飞行仿真平台概要设计》《CONTEXT.md》、ADR-0001～0013
> 编制原则：所有代码修复遵循 TDD（先写失败测试 RED → 最少实现 GREEN → 全绿后重构）；不修改 BlueSky 核心源码；文档与代码同步修订。

## 0. 核对结论

原方案不能作为“首版一次性全部实施”的清单。G1～G18 中多数是首版详细设计已经明确简化、但总体设计仍保留的后续能力；若全部作为 P0/P1 缺陷处理，会改变已经确认的首版范围和指令语义。核对后采用以下处置：

| 类别 | 核对结果 |
|---|---|
| 立即采纳 | 统一三份文档的首版简化口径；使用真实 MySQL 解除启动阻塞；忽略本地 `sql_backup/`；修复本轮复现出的 5 个实现缺陷 |
| 延后实施 | WP-1～WP-13 保留为总体设计后续工作包，不作为当前单组、单席位、五类核心指令闭环的完成门槛 |
| 不采纳 | 不把总体需求直接改成首版必做；不在证据不足时把 Q01～Q26 全部标记通过；不转换已经是 UTF-8 的 `wiki/已实现宏指令2.txt`；不删除作为需求来源的 PDF/XLSX 文件 |

本轮按 TDD 修复了以下真实缺陷：

1. Adapter `RESET` 未清除旧 `RTE` 回执，同呼号重建后可能携带过期 `routeChange`；
2. Java 启动复位在健康检查后 Adapter 瞬时断开时会导致平台启动失败；
3. 可选二次代码传空字符串时没有归一化为缺失值；
4. 排队的 `ALT ... VS ...` 在真正下发时没有按最新高度重新确定升降率符号；
5. 标牌正北航向显示为 `000`，与已确认的 `360` 显示规则不一致。

上述修复均先增加失败测试，再实施最小修复。它们不扩张首版功能范围。

## 1. 方案目标

1. 将 G1～G18 分类为“首版缺陷”或“后续总体能力”，不再混为一类；
2. 消除首版直接实现文档与当前代码之间的真实不一致；
3. 解除 T24 的 MySQL 启动阻塞并保留尚未完成的人工验收边界；
4. 处理不影响需求来源文件的仓库卫生项。

判定顺序为：《首版飞行仿真闭环详细设计》是当前直接实现与验收基线；概要设计、CONTEXT 和 ADR 是总体设计基线。总体能力尚未进入首版时，应在详细设计中登记简化边界，而不是把未实现的总体能力一律判为首版代码缺陷。

### WP-1 单位语义（G1，后续草案）

**设计**：输入侧（前端表单 + 短指令解析）实施“默认米制/千米每小时 + 显式后缀”，平台协议字段保持英制（`altitudeFeet`、`speedKnots`、`verticalSpeedFeetPerMinute`），Adapter 边界不变。

**换算系数（集中常量，禁止散落）**：
- 高度：`1 m = 3.280839895 ft`
- 速度：`1 km/h = 0.539956803 kt`
- 升降率：`1 m/s = 196.8503937 ft/min`

**改动点**：

| 层 | 文件 | 改动 |
|---|---|---|
| 后端 | `instruction/InstructionParser.java` | `ALT <h>[FT] [VS <r>[FPM]]`：h 默认米→ft，`FT` 后缀直用；r 默认 m/s→fpm，`FPM` 后缀直用；`SPD <v>[KT]`：默认 km/h→kt；`MACH` 不变；非法后缀/负数按现有 400 规则拒绝。错误信息携带“当前默认单位”提示 |
| 后端 | `instruction/InstructionResponse.java`（可选） | 增加 `normalizedPayload` 展示换算后的协议值，便于联调核对 |
| 前端 | `CreateAircraftDialog.vue` | 高度/速度输入改为文本输入（可带 `FT`/`KT` 后缀），输入框旁常驻显示“默认：米 / 千米每小时”；提交前换算为 `altitudeFeet/speedKnots` 数值 |
| 前端 | `aircraftForm.ts` | 新增 `normalizeAltitude/normalizeSpeed` 纯函数（默认单位 + 后缀解析 + 范围校验） |
| 前端 | 指令输入 | 不需改动（原始文本由后端解析，符合“任何层不得按数值猜单位”） |

**测试（RED→GREEN）**：
- 后端新增 `InstructionParserUnitTest`：`ALT 9000`→29527.559 ft；`ALT 30000FT`→30000 ft；`ALT 9000 VS 10`→1968.504 fpm；`ALT 30000FT VS 1500FPM`→1500 fpm；`SPD 500`→269.978 kt；`SPD 280KT`→280 kt；`SPD 500KPH`→拒绝；`ALT -100`→拒绝。
- 前端 `aircraftForm.test.ts` 补单位用例。
- 回归：`InstructionApiTest` 现有用例按新语义更新期望值（`ALT 12000` 将变为 39370 ft，需同步修 `validAircraftBody` 与验收示例）。

**风险与回滚**：语义变化影响现有联调数据；回滚 = 恢复 D1=B 并回退本 WP 与 WP-0 相应文档段落。

### WP-3 完成判据与稳定窗口（G3，后续草案）

**设计**：在 Java 侧实现轻量 `CompletionMonitor`（阶段 B 的 WP-7 会把它并入完整状态机，本 WP 只做首版最小实现）。

**规则（按 CONTEXT L588-591）**：
- `HDG`：磁航向圆周差 ≤1° 且连续稳定 2 s（1 Hz 下 ≥3 个连续合格样本）；
- `ALT`：|Δ高度| ≤100 ft 且 |升降率| ≤100 fpm，稳定 3 s（≥4 个样本）；
- `SPD`：|ΔIAS| ≤5 kt 稳定 3 s；`MACH`：|ΔM| ≤0.01 稳定 3 s；
- 任一中间样本不合格立即清零重算；稳定计时用训练组仿真时间（首版由 1 Hz 状态帧驱动，暂停时无帧推进，天然满足冻结语义）。

**参数化**：`system_parameter` 新增键（Flyway 迁移，与 WP-4 合并为 V4）：
`completion.hdg.toleranceDeg=1`、`completion.hdg.stableSeconds=2`、`completion.alt.toleranceFt=100`、`completion.alt.vsToleranceFpm=100`、`completion.alt.stableSeconds=3`、`completion.spd.toleranceKt=5`、`completion.spd.stableSeconds=3`、`completion.mach.tolerance=0.01`、`completion.mach.stableSeconds=3`。

**改动点**：
- 新增 `instruction/CompletionMonitor.java`：按 `aircraftId+channel` 维护样本计数（内存态，启动复位清空；首版不跨进程持久化，WP-7 再决策持久化）。
- `InstructionProgressService.evaluate` 改为：满足容差→计数+1；不满足→清零；计数达阈值→COMPLETED。新指令开始执行时重置该通道窗口。
- `AdapterStateProjector` 仅在 RUNNING 状态帧推进判定（READY/PAUSED 时冻结，防御性）。

**测试**：新增 `CompletionMonitorTest`：连续 3 个合格样本才完成；第 2 个不合格清零重算；跨通道互不影响；参数从 `system_parameter` 读取。

**不包含**（进入 WP-7）：双层超时（`ADAPTER_ACK_TIMEOUT`/`TIMED_OUT`）、`DISPATCHING` 持久化、失败依赖队列。

### WP-7 指令状态机重构（G8/G14/G18 + 概要设计 §8.5-8.8 全量）

**范围**（阶段 B 核心，规模 XL）：
1. 状态全集：`RECEIVED/VALIDATED/WAITING_FOR_RESUME/WAITING_FOR_PREDECESSOR/DISPATCHING/EXECUTING/COMPLETED/REPLACED/FAILED/TIMED_OUT/CANCELLED/REJECTED` + 原因码（`ADAPTER_ACK_TIMEOUT`、`QUEUE_WAIT_TIMEOUT`、`QUEUE_CLEARED_BY_REPLACE`、`CHANNEL_DISPATCH_IN_PROGRESS`、`BUSINESS_FIELD_*` 等）；
2. 异步下发：`DISPATCHING` 持久化、5 s 技术确认超时（系统时间）、同冲突键在途下发占位、幂等键（`Idempotency-Key`）与载荷一致性（`IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`）；
3. 双层超时：`HDG/ALT/SPD/MACH` 按概要设计 8.7 公式与上下限（300/1800/600 s）计算业务超时，训练组仿真时间计时、暂停冻结；
4. 暂停语义（G8）：新指令进入 `WAITING_FOR_RESUME` 不下发；
5. 覆盖生效点：确认成功事务内共同提交新 `EXECUTING` + 旧 `REPLACED` + 旧等待 `CANCELLED/QUEUE_CLEARED_BY_REPLACE`；
6. 排队等待预算（max(300, Σ前置剩余+300)，上限 8 h，首次入队固化，不可重置）；
7. 失败依赖队列（默认依赖成功、失败暂停、教员处置接口留位）；
8. 事务原子性（G18）：完成→下发后继→后继置 EXECUTING 与状态帧投影放入同一短事务边界，杜绝“引擎已执行但平台状态未更新”的残留停摆；
9. SSE 事件 ID（G14）：`SseEmitter.id(...)` 每事件递增稳定 ID，为智能机长 `Last-Event-ID` 续传预留。

**验收**：把概要设计 §23 的 AT-13/AT-15/AT-16/AT-17 转为首版测试（`InstructionStateMachineTest`、`DispatchReservationTest`、`QueueWaitBudgetTest`、`PauseInstructionTest`、`SseEventIdTest`），逐条 RED→GREEN。

**风险**：本 WP 会替换现有 `InstructionService` 同步路径；必须保留现有 12 个 `InstructionApiTest` 用例语义（迁移为状态机用例），并保证 IMMEDIATE/AFTER_CURRENT/APPEND 三个快捷键行为不变。
